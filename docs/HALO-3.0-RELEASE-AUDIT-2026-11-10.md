# HaloTV 3.0 发布前检查报告

检查日期：2026-11-10  
范围：当前本地最新正式版 Guard、Standard，以及 Lite。基线提交：0ef654f。  
本轮目标：优先操作流畅和视觉衔接，允许合理的小尺寸缓存，不删减现有功能和动画。

## 一、结果与交付

三个 Release 安装包已构建成功，自动测试和 Android 静态检查均无错误；手机网页脚本语法检查通过。可进入下一轮电视测试。

本轮没有安装到电视、运行模拟器、发布 GitHub 或修改官网更新信息。源码检查和自动测试不能代替真实电视的解码、遥控器、冷启动和长时间运行测试；这里的结论不等于所有品牌已经无卡顿、无闪屏。

## 二、本轮确认并修复的问题

### 1. 毛玻璃处理可能提前释放仍被使用的原图（正式版、Lite）

Android 缩放图片时，如果输入已经是 320×180，可能直接返回输入对象。原逻辑在生成毛玻璃副本后会释放这个对象，但视频画面缓存、返回桌面的保留图仍可能使用它。

现在仅释放临时生成的缩放图，保留调用方拥有的原图。增加回归测试，验证小尺寸视频帧可以重复生成毛玻璃，原图不会被回收。这是明确的图片生命周期错误，能造成后续绘制异常；但不能据此认定所有用户的黑屏均来自这一处。

### 2. 毛玻璃模糊算法重复计算过多（正式版、Lite）

将每个像素重复遍历整个模糊窗口，改为滚动累加计算。保持原来的尺寸、半径、三次模糊、透明通道、边缘处理与取整结果，复用中间数组，减少重复运算与分配。

自动测试覆盖不同尺寸、透明颜色、边缘、半径和多次模糊，与独立的原算法逐像素比较一致。没有通过降低画质或取消模糊实现提速。

本机 JVM 独立基准：320×180、半径 7、连续三次模糊，预热后五轮中位数，原计算 6.787 ms，新计算 1.123 ms，约 6.04 倍。此数字只代表 Mac 上这一段算法，不能换算成电视整机帧率或总体提速倍数。

### 3. 极宽、极高图片可能产生过大的解码内存（正式版、Lite）

普通图片按显示需求采样；额外对极端长宽比增加像素预算，避免一张全景长图解码出大量最终不可见的像素。普通 1080p、常见 4K 图片的既有采样策略保持一致。

覆盖了 80,000×2,000、2,000×80,000 等极端尺寸及整数边界。它能降低图片解码的内存风险，不代表可以承诺任意异常文件都不会出错。

### 4. 视频画面复制取消或失败时的资源清理（正式版）

增加画面复制的完成/废弃状态管理：请求失败或页面切换取消后，等待渲染器结束写入再释放无用图片，避免提前回收与遗留临时画面。成功复制的图片交给原调用方继续使用。

新增完成顺序、取消顺序、重复通知和成功交接测试。

### 5. 视频切换期间旧采样回写毛玻璃（正式版）

毛玻璃采样后会短暂等待并评估掉帧情况。等待期间若播放器或影片已经更换，现在放弃旧评估，防止旧影片的画面/性能结果被用于新影片。

同时释放生成静态电影毛玻璃时的中间缩放图，保留仍有用途的缓存。

### 6. Lite 照片屏保退出后仍有任务回写

解码任务可能在屏保关闭后才完成，原逻辑仍可能更新已退出的视图、重新安排轮播。现在退出会标记屏保已释放，取消计时与动画，清除播放器监听和画面引用；迟到的图片会直接释放，不再恢复轮播。

也补充了空素材、重复退出、播放失败后回退到时钟的保护，减少关闭页面后的无效工作。

### 7. Lite 联网任务阻塞本地界面加载

天气、每日壁纸网络获取和在线图标库刷新，从本地壁纸/应用图标加载队列中拆出。网络慢时不再让本地加载在其后排队。增加一个串行联网工作队列，接受少量线程资源换取响应稳定；没有给每项网络任务无限创建并行线程。

活动销毁时停止队列、丢弃失效回调。壁纸请求增加代次检查，避免快速切换后旧结果覆盖新选择。

### 8. Lite 控制中心的重复绘制分配

壁纸入口横幅的图片着色器、变换矩阵和矩形改为复用，只在尺寸变化时重算；焦点重绘不再每帧重新创建这些对象。版式与图片显示效果不变。

### 9. 每日壁纸缓存被读取到一半（正式版、Lite）

每日壁纸索引和缓存通过临时文件完整写入后再替换发布，降低后台刷新与页面同时读取时读到半份 JSON 或半张图片的风险。失败时清理临时文件。

相关文件写入测试验证完整替换，以及失败后的临时文件清理。每日壁纸网络请求无论成功失败都会关闭连接。

### 10. Lite 已选择的历史每日壁纸被滚动清理

每日缓存只保留近期记录时，原来有可能把用户明确选择的较早日期图片一并清理。现在额外保留当前选中的历史日期和版权信息，使它不因跨日刷新自动消失。

### 11. Lite 本地屏保选择器的迟到缩略图

翻页或关闭后才完成的缩略图解码结果，现在会释放，不再保留无效结果。

### 12. Lite 更新状态的过期结果回写

检查本地待安装包与联网检查可能异步交错。增加请求代次、更新对象与检查/下载状态校验，旧结果不能覆盖新版本状态；联网检查期间不启动基于旧信息的下载。

## 三、流畅度与内存的取舍

- 保留既有焦点动画、毛玻璃效果、当前视频帧与有助于返回桌面的缓存。
- 正式版已有的播放器暂停保留、首帧交接和返回海报机制继续保留，本轮没有反向改成频繁清空缓存。
- 返回桌面的中间画面、毛玻璃和小图缓存按用途保留；过期任务和不再使用的临时图及时释放。
- 进入其他应用时仍释放可能与视频应用争抢的解码资源。不同电视的硬件解码器数量有限，同时后台解码两路 4K 视频可能影响正在观看的内容。
- 维持现有界面画布与自适应布局，不恢复曾导致卡顿的强制实验性 4K 画布。
- 正式版保持三种性能模式；Lite 保持较轻的实现，不为视觉一致性引入正式版播放器/Compose 依赖。
- Release 仍启用代码和资源压缩。本轮正式包相较上一轮本地包只增加约 1.5 KB，没有靠删除界面功能压缩体积。

## 五、仍存在的静态告警

Standard：273 Warning、16 Hint；Guard：274 Warning、16 Hint；Lite：376 Warning。

主要是未使用资源、写法建议、平台反射接口、自绘 View 构造与绘制分配、静态 Context 持有提示等。这些不等同于相同数量的已确认运行故障。例如部分静态对象保存的是 applicationContext，不应只凭告警名称就认定为 Activity 泄漏；未使用资源也已经由 Release 资源压缩器处理。

本轮优先修复能确认的生命周期、图片所有权、并发与计算开销。没有为清零提示而大范围更换厂商接口或重写稳定代码。厂商私有接口与少量非连续绘制的分配建议仍需要分设备、分收益处理；完整告警已保留，不能把此次检查称为“所有告警为零”。

## 六、发布前仍需电视确认的重点

1. 动态桌面：使用本地视频，连续进入/退出控制中心、设置、弹窗及屏保；再从一个视频应用返回桌面，观察是否黑帧、旧帧、长时间模糊或停止播放。1080p H.264 和电视可播放的 4K 编码各试一次。
2. 常用遥控操作：快速左右切应用、下翻全部应用再返回、打开多个层级设置后返回，查看焦点、Dock 与背景是否稳定。
3. Lite：连续进出照片/翻页时钟屏保、翻本地照片选择器、联网较慢时更换本地壁纸，确认页面能及时响应。
4. 儿童与长辈：进入、退出、密码确认、答题、时间上限、休息提示、屏保/待机后不自动重新进入已退出模式。
5. 更新：用同签名更高内部号包测试手机推送、自动下载完成提示与安装确认；尝试其他应用 APK 或旧版，确认拒绝。当前 3.0 测试包无需现在公开发布来完成检查。
6. 守护：电视完全断电重启、待机唤醒、从系统设置/信号源按 Home；有条件再观察隔日是否仍有效。静态代码不能替代这类跨日实测。

本轮没有获取电视 PSS/RSS、CPU、GPU、帧率、掉帧或长期运行曲线，因此不提供虚构的整机内存/流畅度数字。若上述实机项目仍有异常，应保留对应操作与日志继续定位，避免凭目测把每个黑帧都归因于同一模块。

## 七、后续发布注意

本轮不修改官网/GitHub 的公开版本，防止测试包提前推给所有用户。正式发布时应同时同步三个包、SHA-256、各自内部版本号、官网更新清单、版本说明和仓库主页。尤其此次显示版本仍为 3.0，应确保更新清单提供新的内部号，否则单靠显示版本字符串可能无法通知已安装旧 3.0 的用户。

项目文件夹中的三个 APK 是本轮新编译的发布候选测试包；安装前无需卸载同签名旧 HaloTV。先保留已有数据进行覆盖测试，更能发现真实升级问题。
